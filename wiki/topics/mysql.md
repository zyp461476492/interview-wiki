### mysql-001
- 难度：基础 | 考点：SQL 执行流程、Server 层组件、存储引擎层
- 题目：MySQL 中一条 SQL 语句的执行流程是怎样的？请简述 Server 层各组件的作用，以及存储引擎层与 Server 层的关系。
- 首次生成：2026-08-04 | 来源：question/2026-08-04-mysql-1.md

#### 参考答案
- **整体分层**：MySQL 分为 Server 层（覆盖连接、解析、优化、执行等，所有存储引擎共用）和存储引擎层（负责数据的实际存取，可插拔，如 InnoDB/MyISAM）。
- **一条 SQL（查询）执行流程**：
  1. **连接器**：建立/校验客户端 TCP 连接，鉴权用户权限，获取连接（长连接复用，受 `wait_timeout` 控制）。
  2. **查询缓存**（MySQL 8.0 已移除）：以「SQL 文本 + 库表」为 key 查缓存，命中直接返回；因命中率低、更新即失效，8.0 起彻底废弃。
  3. **分析器**：词法分析（识别关键字、表名、列名）+ 语法分析，生成解析树，校验语法/表/列是否存在，权限校验。
  4. **优化器**：生成执行计划——选择索引、决定表连接顺序、估算成本，基于规则与成本（CBO）。决定用哪个索引、是否走全表扫描。
  5. **执行器**：调用存储引擎接口，逐行取数据；先判断操作权限（行级权限），再按执行计划调引擎的 `read`/`update` 接口。执行器是一个「调用者」，引擎是「实际干活者」。
  6. **存储引擎层**：InnoDB 等负责真正读写数据页（B+ 树）、维护缓冲池（Buffer Pool）、事务/锁/MVCC。
- **Server 与存储引擎关系**：Server 层处理连接、解析、优化、执行调度；存储引擎提供数据存取抽象（通过 Handler API）。一个 SQL 的优化计划由 Server 决定，但实际数据读写由引擎完成，引擎的索引/锁/MVCC 能力反过来制约优化器选择。
- **更新语句额外流程**：写入 redo log（prepare）→ 写 binlog → redo log（commit），即「两阶段提交」，保证 crash-safe（详见 mysql-007）。

### mysql-002
- 难度：基础 | 考点：InnoDB vs MyISAM、默认存储引擎
- 题目：InnoDB 与 MyISAM 存储引擎有哪些主要区别？为什么 MySQL 5.5 之后默认存储引擎改为 InnoDB？
- 首次生成：2026-08-04 | 来源：question/2026-08-04-mysql-1.md

#### 参考答案
- **主要区别**：

  | 维度 | InnoDB | MyISAM |
  |------|--------|--------|
  | 事务 | 支持事务（ACID） | 不支持事务 |
  | 锁粒度 | 行锁/表锁（默认行锁，高并发优） | 仅表锁（写并发差） |
  | 外键 | 支持 | 不支持 |
  | 索引结构 | 聚簇索引（数据和主键索引一起存） | 非聚簇索引（索引与数据分离） |
  | 崩溃恢复 | 支持 crash-safe（redo log） | 崩溃易损坏，恢复慢 |
  | 全文索引 | 5.6 后支持 | 支持 |
  | 适用场景 | 高并发写、事务、一致性要求高 | 只读/读多写少、无事务需求 |
- **默认改用 InnoDB 的原因**：
  1. **事务与一致性**：现代应用几乎都需事务，InnoDB 是唯一支持 ACID 的默认可用引擎。
  2. **高并发性能**：行锁让读写并发远优于 MyISAM 的表锁，适合 OLTP。
  3. **崩溃恢复**：redo log 保证 crash-safe，MyISAM 崩溃后表损坏概率高。
  4. **外键约束**：保障引用完整性。
  5. **生态趋势**：功能已逐步补齐（全文索引、5.6+ 支持全文索引），性能在并发场景下全面优于 MyISAM。
- **补充**：MyISAM 仅在纯只读、历史归档等极少场景仍有优势（表级统计快、COUNT(*) 无需扫行）。

### mysql-003
- 难度：基础 | 考点：ACID 特性、InnoDB 保证机制
- 题目：简述事务的 ACID 特性。InnoDB 分别通过什么机制来保证这四个特性？
- 首次生成：2026-08-04 | 来源：question/2026-08-04-mysql-1.md

#### 参考答案
- **ACID 四特性**：
  - **A（原子性 Atomicity）**：事务是一个不可分割单元，要么全做要么全不做。
  - **C（一致性 Consistency）**：事务执行前后，数据库从一个合法状态变为另一个合法状态（约束、完整性不破坏）。
  - **I（隔离性 Isolation）**：并发事务之间互不干扰，一个事务的中间状态对其他事务不可见。
  - **D（持久性 Durability）**：事务一旦提交，对数据的修改是永久的，即使宕机也不丢失。
- **InnoDB 的保证机制**：
  - **A 原子性**：通过 **undo log（回滚日志）**。事务修改前先写 undo log，记录修改前镜像；若回滚则据 undo log 反向操作还原。崩溃恢复时未提交的事务也会用 undo log 回滚。
  - **D 持久性**：通过 **redo log（重做日志）** + Buffer Pool 的 **WAL（Write-Ahead Logging）**。修改先写 redo log（顺序写、持久化）再写数据页，即使数据页未刷盘，崩溃后可用 redo log 重做恢复。
  - **I 隔离性**：通过 **锁机制**（行锁/间隙锁解决写写冲突）+ **MVCC（多版本并发控制）**（解决读写冲突，快照读不加锁）。不同隔离级别用不同策略。
  - **C 一致性**：是最终目标，由 A + D + I + 应用层约束（约束、触发器、外键）共同保证。AID 是手段，C 是结果。
- **一句话**：undo log 保 A、redo log 保 D、锁+MVCC 保 I，三者合力保 C。

### mysql-004
- 难度：进阶 | 考点：B+ 树索引结构、索引数据结构对比
- 题目：为什么 MySQL InnoDB 索引使用 B+ 树？请与 B 树、Hash 索引、红黑树对比分析其优劣。
- 首次生成：2026-08-04 | 来源：question/2026-08-04-mysql-1.md

#### 参考答案
- **B+ 树特点**：非叶节点只存索引（不存数据），所有数据都在叶节点；叶节点用双向链表有序连接；树矮胖，每层用页（默认 16KB）存大量索引项，故层数少（通常 3 层可存千万级）。
- **B+ 树 vs B 树**：
  - B 树非叶节点也存数据，单页能放的索引键少 → 树更高 → IO 次数多。
  - B+ 树数据只在叶子，非叶能放更多键，树更矮；叶节点链表使**范围查询**（`between`/`>`/`order by`）只需遍历链表，B 树需中序遍历回溯，效率低。
  - B+ 树查询稳定（每次都查到叶子），B 树非叶命中即返回，性能波动。
- **B+ 树 vs Hash 索引**：
  - Hash O(1) 等值查询极快，但不支持范围查询、前缀匹配、排序（`order by`）、`LIKE` 前缀，且无法用于避免 `order by` 的 filesort。
  - Hash 索引不支持最左前缀，冲突多时退化；且不支持范围扫描。InnoDB 主键/二级索引都基于 B+ 树；Hash 适配是内部的**自适应哈希索引（AHI）**，仅对热点等值查询加速，非用户索引。
  - Hash 适合等值精确（如 KV 存储的 memcached），B+ 树通用性更强，契合关系数据库的范围/排序需求。
- **B+ 树 vs 红黑树/二叉树**：
  - 二叉树（含红黑树）每个节点只有 2 个子节点，数据量大时树高（log₂N）很大，百万级数据树高约 20，即最多 20 次磁盘 IO，性能差。
  - B+ 树是多叉（数百叉），3 层即可存约 2000 万行（每页放 ~1170 个键 × 三层），IO 次数 = 树高，远优于二叉树。
  - 数据库以**页（16KB）**为单位 IO，B+ 树的节点恰好对齐页，一个节点一次 IO，最契合磁盘的「按页读取」特性。二叉树无法利用页的批量读取。
- **结论**：B+ 树在「磁盘 IO 友好、范围查询高效、树矮稳定、扇出大」四方面契合数据库场景，故 InnoDB 选 B+ 树。

### mysql-005
- 难度：进阶 | 考点：聚簇索引/非聚簇索引、回表、覆盖索引
- 题目：什么是聚簇索引和非聚簇索引（二级索引）？什么是回表？如何通过覆盖索引避免回表？请举例说明。
- 首次生成：2026-08-04 | 来源：question/2026-08-04-mysql-1.md

#### 参考答案
- **聚簇索引（Clustered Index）**：索引与数据行一起存储，即「叶节点存的是整行数据」。InnoDB 的主键索引即聚簇索引；一张表只有一个聚簇索引（按主键建）。若未定义主键，InnoDB 选第一个唯一非空索引；都没有则隐式生成 `row_id`。
- **非聚簇索引 / 二级索引（Secondary Index）**：叶节点存的是「索引列值 + 主键值」，不直接存整行数据。需要再回主键索引查整行。
- **回表**：通过二级索引查到主键 → 再到聚簇索引按主键查整行数据的过程。回表 = 多一次 B+ 树查找。
- **覆盖索引（Covering Index）**：若查询的列全部能被某索引覆盖（即索引列包含 `select` 所需所有列），引擎只需在二级索引叶节点取数据，无需回表。EXPLAIN 的 Extra 会显示 `Using index`。
- **举例**：表 `user(id PK, name, age, city)`，建索引 `idx_name_age(name, age)`。
  - `select name, age from user where name = 'Tom'`：查询列 name、age 都在索引中 → 覆盖索引，`Using index`，无回表。
  - `select * from user where name = 'Tom'`：查所有列含 id、city 等 → 需用主键回表到聚簇索引取整行（`Using index condition` 或无 `Using index`）。
  - `select name, age, city from user where name = 'Tom'`：city 不在索引中 → 仍需回表。若改建联合索引 `idx_name_age_city(name,age,city)` 则又变覆盖索引。
- **意义**：覆盖索引减少一次回表（少一次 B+ 树查找与随机 IO），对高频查询性能提升明显。设计时应优先让热点查询走覆盖索引。
- **补充**：最左前缀原则——联合索引 `(a,b,c)` 可匹配 `a`、`(a,b)`、`(a,b,c)`，不能跳过 a 直接用 b；遇到范围查询则后续列失效。索引下推 ICP（5.6+）把 where 条件下推到引擎层在索引上过滤，减少回表次数。

### mysql-006
- 难度：进阶 | 考点：隔离级别、并发问题、MVCC、ReadView
- 题目：MySQL 的四种事务隔离级别分别解决了哪些并发问题？什么是 MVCC？InnoDB 在 RC 和 RR 下如何通过 ReadView 实现快照读？
- 首次生成：2026-08-04 | 来源：question/2026-08-04-mysql-1.md

#### 参考答案
- **三种并发问题**：
  - **脏读**：读到其他事务未提交的数据，若该事务回滚则读到的是无效数据。
  - **不可重复读**：同一事务内两次读同一行结果不同（被别的事务修改并提交了）。
  - **幻读**：同一事务两次范围查询结果集行数不同（被别的事务 insert/delete 提交了）。
- **四种隔离级别**（SQL 标准，由低到高）：

  | 隔离级别 | 脏读 | 不可重复读 | 幻读 |
  |----------|------|-----------|------|
  | 读未提交 RU | 可能 | 可能 | 可能 |
  | 读已提交 RC | 解决 | 可能 | 可能 |
  | 可重复读 RR（InnoDB 默认） | 解决 | 解决 | InnoDB 基本解决（间隙锁） |
  | 串行化 Serializable | 解决 | 解决 | 解决 |
- **MVCC（多版本并发控制）**：通过给每行加隐藏的「版本号/事务 ID」+ undo log 链（历史版本），让读操作读历史快照而不加锁，从而读写不互斥，提升并发。MVCC 仅对**快照读**（普通 select）生效；**当前读**（`for update`/`lock in share mode`/update/delete）读最新已提交数据并加锁。
- **行版本链（undo log 版本链）**：每行有 `trx_id`（最后修改它的事务 id）、`roll_pointer` 指向 undo log 中的上一版本，形成链表。
- **ReadView**：事务执行快照读时生成的「可见性判断视图」，包含：
  - `m_ids`：生成 ReadView 时当前活跃（未提交）事务 id 列表。
  - `min_trx_id`：m_ids 中最小值；`max_trx_id`：下一个要分配的事务 id。
  - `creator_trx_id`：当前事务 id。
- **可见性规则**：取某版本 trx_id 记为 t：
  - t == creator_trx_id → 自己改的，可见。
  - t < min_trx_id → 该版本在 ReadView 之前已提交 → 可见。
  - t ≥ max_trx_id → 该版本是 ReadView 之后才产生 → 不可见。
  - min_trx_id ≤ t < max_trx_id 且 t 在 m_ids 中 → 未提交 → 不可见；不在 m_ids 中 → 已提交 → 可见。
  - 不可见则顺 roll_pointer 找上一版本重复判断。
- **RC 与 RR 的关键区别**：
  - **RC（读已提交）**：**每次快照读都生成新 ReadView**，所以能看到别的事务的最新已提交 → 解决脏读，但同一事务内两次读可能不同（不可重复读未解决）。
  - **RR（可重复读）**：**事务内第一次快照读时生成 ReadView，后续复用同一个**，所以整个事务看到的快照一致 → 解决不可重复读。
- **幻读**：InnoDB 在 RR 下用**间隙锁/临键锁**对当前读的范围加锁，阻止别的事务 insert，配合 MVCC 快照读基本消除幻读；但若先快照读再当前读可能仍感知「幻行」（少数边界）。

### mysql-007
- 难度：进阶 | 考点：redo log/undo log/binlog、两阶段提交、crash-safe
- 题目：简述 MySQL 中 redo log、undo log、binlog 的作用与区别。为什么需要两阶段提交（2PC）？如何保证 crash-safe？
- 首次生成：2026-08-04 | 来源：question/2026-08-04-mysql-1.md

#### 参考答案
- **三种日志**：

  | 日志 | 层级 | 作用 | 内容 | 写入方式 |
  |------|------|------|------|----------|
  | **redo log** | InnoDB 引擎层 | 保证持久性（crash-safe），记录「页的物理修改」 | 顺序写、循环写，固定大小（如 2 个文件轮转） | WAL，先写 redo log（prepare）再写数据页 |
  | **undo log** | InnoDB 引擎层 | 保证原子性（回滚）+ MVCC（多版本） | 记录修改前的逻辑反向操作与历史版本，存于回滚段 | 随事务写 |
  | **binlog** | Server 层 | 主从复制 + 数据归档恢复 | 记录「逻辑操作」（SQL/行变更），追加写、循环追加 | 事务提交后写 |
- **核心区别**：redo/undo 属 InnoDB 引擎层，binlog 属 Server 层（所有引擎共用）；redo 是物理日志、binlog 是逻辑日志；redo 循环写（覆盖旧）、binlog 追加写不覆盖；redo 保证 crash-safe，binlog 主用于复制与 PITR（按时间点恢复）。
- **为什么需要两阶段提交（2PC）**：让 redo log 与 binlog 的提交状态一致，避免主从数据不一致。
  - 若先写 redo 后 commit、再写 binlog：redo 写完崩溃，binlog 未写 → 主库回滚（无数据），但从库未同步该事务 → 从库少数据 → 主从不一致。
  - 若先写 binlog 再写 redo：binlog 写完崩溃，redo 未写 → 主库回滚（无数据），但 binlog 已写 → 从库重放该事务 → 从库多数据 → 主从不一致。
  - **2PC 流程**：① 写 redo log（prepare 状态）；② 写 binlog；③ 提交事务（redo log 改为 commit 状态）。崩溃恢复时判断：prepare 状态的 redo log 是否有对应 binlog——有则提交、无则回滚。这样保证 redo 与 binlog 一致，主从一致。
- **crash-safe**： redo log 的 WAL 机制——事务提交时 redo log 已落盘（`innodb_flush_log_at_trx_commit=1`），即使数据页还没刷盘，崩溃后用 redo log 重做已提交事务、用 undo log 回滚未提交事务，从而恢复到一致状态。
- **binlog 三种格式**：statement（SQL 语句，可能函数不确定导致主从不一致）、row（行变更，安全但日志大，默认）、mixed（混合）。

### mysql-008
- 难度：实战 | 考点：慢 SQL 优化、EXPLAIN、索引失效
- 题目：如何排查和优化一条慢 SQL？请说明 EXPLAIN 中 type、key、rows、Extra 等关键字段的含义，并列举常见索引失效场景。
- 首次生成：2026-08-04 | 来源：question/2026-08-04-mysql-1.md

#### 参考答案
- **排查思路**：
  1. 开启慢查询日志（`slow_query_log=ON`，`long_query_time`），定位慢 SQL。
  2. `EXPLAIN` 分析执行计划，重点看是否走索引、扫描行数、Extra。
  3. 必要时 `EXPLAIN ANALYZE`（8.0）/ `SHOW PROFILE` / `performance_schema` 看耗时环节（锁/IO/排序/临时表）。
  4. 优化方向：加/改索引、改写 SQL、避免大事务、分页优化、SQL 重写。
- **EXPLAIN 关键字段**：
  - **id**：查询序号，id 相同从上往下执行；id 越大越先执行（子查询/派生表）。一般希望复杂查询 id 渐进。
  - **select_type**：查询类型（SIMPLE/PRIMARY/SUBQUERY/DERIVED 等）。
  - **type**（访问类型，性能由好到差）：`system`/`const`（主键/唯一索引等值）> `eq_ref`（被连接表主键/唯一索引等值，最多 1 行）> `ref`（非唯一索引等值）> `range`（范围扫描）> `index`（扫描整棵索引树）> `ALL`（全表扫描，最差）。一般要求至少 `range`/`ref`，避免 `ALL`。
  - **possible_keys**：可能用到的索引；**key**：实际用到的索引（NULL 表示没走索引）。
  - **key_len**：使用的索引长度（字节数），判断联合索引用了几列。
  - **ref**：索引比较的常量/列。
  - **rows**：估算扫描行数，越小越好。
  - **filtered**：过滤后剩余比例（8.0）。
  - **Extra**：额外信息。`Using index`（覆盖索引，好）；`Using where`（用 where 过滤）；`Using index condition`（索引下推 ICP）；`Using filesort`（需额外排序，需优化）；`Using temporary`（用了临时表，需优化）。
- **常见索引失效场景**：
  1. 对索引列做函数/运算：`where year(create_time)=2024`、`where id+1=10` → 失效。改为 `where create_time >= '2024-01-01' and ...`。
  2. 隐式类型转换：字符串列 `where phone = 13800000000`（数字传字符串列）→ 失效。
  3. `LIKE` 以 `%` 开头：`where name like '%Tom'` → 失效（`'Tom%'` 可用）。
  4. 不符合最左前缀：联合索引 `(a,b,c)` 用 `where b=1`（跳过 a）→ 失效；范围查询后列失效如 `where a=1 and b>10 and c=2`（c 失效）。
  5. `!=` / `<>` / `NOT IN` / `NOT EXISTS`：通常走全表扫描（区分度低时不走索引）。
  6. `OR` 两边非都走索引：`where a=1 or b=2` 若 b 无索引则整体全表扫。
  7. 优化器认为全表更快（返回行数占比大、统计信息陈旧、`ANALYZE TABLE` 更新统计）。
  8. 字符集/排序规则不一致（join 两表同名列规则不同）。
- **优化要点**：避免 `select *`（用覆盖索引）、大分页用延迟关联/游标、`order by` 字段加索引避免 filesort、合理建联合索引、避免回表、定期 `ANALYZE TABLE`。

### mysql-009
- 难度：实战 | 考点：锁机制、间隙锁/临键锁、死锁
- 题目：InnoDB 中有哪些锁（行锁/表锁/间隙锁/临键锁）？什么场景下会产生死锁？如何排查与避免死锁？
- 首次生成：2026-08-04 | 来源：question/2026-08-04-mysql-1.md

#### 参考答案
- **InnoDB 锁的分类**：
  - **按粒度**：
    - **表锁**：锁整张表，并发差。如 `lock tables` 显式锁、DDL 期间的表锁。
    - **行锁**：锁单行（基于索引），并发好。InnoDB 默认行锁（但行锁是加在索引上的，无索引则升级为表锁）。
  - **按类型**：
    - **共享锁（S，读锁）**：`lock in share mode`，可并行读不可写。
    - **排他锁（X，写锁）**：`for update`/update/delete，互斥。
  - **按范围（RR 隔离级别下解决幻读）**：
    - **记录锁（Record Lock）**：锁单条索引记录。
    - **间隙锁（Gap Lock）**：锁索引区间（开区间，不含记录），只防 insert，防别的事务向间隙插数据。
    - **临键锁（Next-Key Lock）**= Record + Gap：锁左开右闭区间，是 RR 下行锁的默认形式，锁记录 + 前面的间隙。
    - **插入意向锁**：insert 前的意向，与间隙锁冲突。
  - **意向锁（IS/IX，表级）**：行锁前先加表级意向锁，目的是快速判断「表上是否有行锁」，避免逐行检查，提升加表锁效率。
- **死锁**：两个或多个事务互相持有对方需要的锁，导致循环等待，谁也无法继续。InnoDB 有死锁检测（`innodb_deadlock_detect=ON`），检测到后回滚代价较小的事务。
- **常见死锁场景**：
  1. 事务以不同顺序锁多行：T1 先锁 A 再锁 B，T2 先锁 B 再锁 A。
  2. 间隙锁冲突：T1 `select ... for update` 给间隙加间隙锁，T2 往该间隙 insert 被阻塞；T1 又等 T2 持有的其他锁 → 死锁。
  3. 唯一索引冲突/insert 触发的 S 锁与别的事务 X 锁互斥。
  4. 大事务长持锁 + 并发 update。
- **排查**：
  - `SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK` 段，含死锁涉及事务、SQL、持有的锁。
  - 开启 `innodb_print_all_deadlocks=ON`，死锁信息写入 error log。
  - `information_schema.INNODB_TRX` / `INNODB_LOCKS` / `INNODB_LOCK_WAITS`（8.0 迁至 `performance_schema.data_locks` 等）查当前事务与锁等待。
- **避免**：
  1. 事务内以相同顺序访问表/行（约定加锁顺序）。
  2. 缩短事务、尽快提交，减少持锁时间。
  3. 走索引避免行锁升级表锁、减少锁范围。
  4. 大批量更新分批、降低并发；改 RC 隔离级别减少间隙锁（需评估一致性）。
  5. 业务上用乐观锁/分布式锁替代 `for update`。
  6. 合理加索引减小 Next-Key Lock 范围。

### mysql-010
- 难度：开放 | 考点：大表优化、分库分表、分区表、读写分离
- 题目：当单表数据量达到千万级，你会从哪些维度进行优化？请对比分库分表、分区表、读写分离等方案的适用场景与权衡。
- 首次生成：2026-08-04 | 来源：question/2026-08-04-mysql-1.md

#### 参考答案
- **先评估是否真的需要分**：MySQL 单表 B+ 树 3 层即可存约 2000 万行，配合索引与合理的硬件，千万级往往不必分库分表；过早分片会引入复杂度。优化优先级：**SQL/索引优化 > 缓存 > 表结构/分区 > 读写分离 > 分库分表**。
- **优化维度**：
  1. **SQL 与索引**：加合适索引、覆盖索引、避免 `select *`、大分页用延迟关联、消除 filesort/临时表、`ANALYZE TABLE` 更新统计。
  2. **表结构**：适度反范式（冗余字段减少 join）、冷热分离、字段类型精简、大字段拆分到附表。
  3. **缓存**：Redis 缓存热点读，降低 DB 压力。
  4. **硬件/配置**：Buffer Pool 调大、SSD、合理 `innodb_buffer_pool_size`/`innodb_io_capacity`。
- **方案对比**：

  | 方案 | 适用场景 | 优点 | 代价/权衡 |
  |------|----------|------|-----------|
  | **读写分离** | 读多写少、读压力大 | 实现相对简单（主从复制+代理）；读可水平扩展 | 主从延迟（写后读一致需走主）；不解决写瓶颈与单表容量 |
  | **分区表（Partition）** | 单表数据多、但查询多按分区键过滤、历史归档 | 对应用透明（一张表）；便于按分区 drop 归档；优化器可分区裁剪 | 单机；不解决并发写瓶颈；分区键必须含在所有唯一索引；跨分区查询/分区键外查询可能扫所有分区 |
  | **垂直分库** | 表多、业务边界清晰 | 按业务拆库，解耦微服务；减小单库表数量/锁竞争 | 跨库 join/事务难做，需 RPC 聚合 |
  | **垂直分表** | 行不宽但列多、冷热列分明 | 热表变窄，单页放更多行，提升缓存命中 | 需 join 拼接 |
  | **水平分表/分库（Sharding）** | 写/容量/并发均超单机上限 | 突破单机瓶颈，理论无限扩展 | 路由复杂、跨片 join/聚合/分页难、分布式事务、全局唯一 ID、迁移扩容（一致性 hash/2 倍扩容）、运维成本高 |
- **选型建议**：
  - 读压力大但写不多 → 优先**读写分离 + 缓存**。
  - 单表大但按时间/地域有天然分片、查询带分区键 → **分区表**或按该维度**水平分表**。
  - 写并发/容量已超单机 → **水平分库分表**（选好分片键，避免热点，如 user_id 哈希；冷热按时间分）。
  - 业务域清晰 → 先**垂直分库**到微服务。
- **分片要点**：分片键选择（高频查询字段、数据均匀、避免热点）、全局 ID（雪花算法/号段模式）、跨片聚合尽量减少、用中间件（ShardingSphere/Vitess）屏蔽路由、数据迁移与扩容预案（一致性 hash 或 2 倍扩容）。
- **权衡点**：分库分表不是银弹，会牺牲事务/join/运维便利性；应在「SQL 优化 + 索引 + 缓存 + 读写分离」做到极限后再考虑，且尽量延迟到真正必要。
